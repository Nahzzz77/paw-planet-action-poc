# 小爪星球宠物互动 POC

这是一个验证“宠物照片 → 统一卡通母版 → 用户确认像不像 → 后续生成固定动作”的 Web 样片。

## 已经能看、能测的内容

- 小灰示例已接入待机、舔爪、喂食和摸头四个入口，每段媒体都有独立回退。
- 个性化宠物的网页发布资产统一为 H.264、yuv420p、576 × 768、30 fps、152 帧、无音轨。原始 SCAIL 成片只作可追溯输入；它没有通过自动接缝验收时，不能直接注册给网页。
- 网页可选择 JPG、PNG 或 WebP 猫咪照片，浏览器先检查格式、尺寸和文件大小，服务端会再验一次真实文件头。
- 已用 OneThingAI 上的 Qwen-Image-Edit-2511 Int8 真实跑通两轮“用户原图 + 仅负责材质的卡通参考 → 卡通母版”，不再使用浏览器滤镜冒充 AI。
- 页面已串联上传、生成状态、左右对照、“像，使用这张”和“不像，不使用”。
- 新用户首次进入是空主页，不再自动挂载小灰图片或四段视频；只有主动点“查看小灰示例”才加载演示资产。确认卡通母版后，这只宠物才进入主页，未确认、拒绝或生成失败都保持空主页。
- POC 会在浏览器中保存已确认任务的 `jobId + 宠物名`，刷新时先显示恢复态，再从服务端重新读取母版和动作分支；不会持久化失效的 Blob URL，也不会在恢复期间闪出小灰。服务端任务目前仍只有一小时内存寿命，正式上线必须换成登录用户、数据库和对象存储。
- 用户通过母版后，系统建立与该母版 SHA-256 精确绑定的待机、舔爪、猫碗喂食和摸头四个独立分支。当前已知橘猫母版可演示 `4 / 4`；其他未有身份档案的母版仍为 `0 / 4`，不会偷换小灰视频。
- 已保存可视工作流和从成功运行中导出的 API 工作流，下次打开不需要重建节点。

## 这次真实试验的结论

试验图是一只成年橘色长毛猫。第一轮 40 步把短毛灰猫模板当成底图，结果错误地继承了短毛身体，已经判定不通过。

第二轮把用户照片改成 `image1` 和初始 latent，灰猫只作为 `image2` 的材质、灯光和背景参考，并启用官方 Lightning 4 步：

- 长毛颈胸鬃毛、耳饰毛、蓬松外轮廓和绿色眼睛已经明显保住，修复了最严重的“长毛变短毛”。
- 脸型仍比原猫更圆、更卡通，不能宣称完全还原。
- 原图没有展示完整尾巴，结果中的大蓬松尾巴是模型推断，不是可核验事实。

第二轮结果保存在 `public/assets/generated/pet-avatar-orange-longhair-qwen2511-v2-fast4.png`，它用于证明长毛特征保真方向，但不再用作动作缓存的确认母版。一旦用户看到并确认的图与生成动作时的母版不是同一个字节哈希，系统就必须拒绝命中旧视频。

为固定动作迁移新增了动作安全母版 `public/assets/generated/pet-avatar-orange-longhair-motion-safe-v3.png`：尾巴收在身体侧后方，双前爪完全露出。已知橘猫照片现在会把这张真实图展示给用户确认，并且只在它的实际 SHA-256 `7aa1e9dcb9b3db7e2c83f5bbca6068185a68ec3fc9feb91d0c9ba1e1668e11db` 一致时复用已有动作。它验证的是所有宠物母版都必须遵守的通用构图规则，不代表上线后要人工逐张修图。

已知橘猫的四分支现在都有真实 GPU 原片，网页接入的是经过统一 30 fps、152 帧首尾锚定的 `anchor30-poc-v2` 版本，因此这一张与档案哈希精确匹配的母版可显示 `4 / 4`。但要说清楚：这四条旧原片的首尾相似度没有达到新发布门禁，目前只能标记为 `POC salvage`，不能拿它们证明“任意新宠物都已自动通过”。对其他宠物仍坚持 `0 / 4`，不会把现成橘猫或小灰视频冒充新宠物成片。

通用中文 `cat_lick_paw_v1` 模板已真实跑通橘猫：输出 `public/assets/generated/cat-lick-paw-orange-longhair-scail2-cn-v1.mp4`，纯执行约 207.3 秒。逐帧检查中尾巴没有抬起或与前爪融合，抬爪、舔舐、放爪和回到中性坐姿完整；长毛、绿色眼睛和橘白花纹保持。该结果验证了“官方工作流与模型 + 我们自己的版本化中文模板 + 自动宠物档案”路线，不再为每只宠物人工写整段提示词。

橘猫待机 `cat_idle_v1` 已在同一台 OneThingAI RTX 4090 上真实跑通：任务 `5c4fc6f2-f13c-450e-b20f-32912f6e793d` 在空队列中执行约 202.8 秒，输出 `public/assets/generated/cat-idle-orange-longhair-scail2-cn-v1.mp4`。成片为 H.264、576 × 768、16 fps、81 帧、5.0625 秒，SHA-256 为 `3fb06a4c32da220e5df9d66e0c6f4a5efcc2857d482ef40fd713c6b428ce116c`。抽帧中长毛、绿眼、橘白花纹、双前爪和镜头保持稳定，眨眼完整，首尾回到近似的中性坐姿；但尾巴中段摆动幅度大于“只有尾尖轻微摆动”的提示词要求，接入正式待机前仍需用户视觉验收。结果下载验证后，实例已再次确认为“已关机、未开始计费”。

橘猫自包含喂食 `cat_feed_v1` 也已完成一次真实 GPU 运行并通过验收。可播放产物为 `public/assets/generated/cat-feed-orange-longhair-scail2-cn-v1.mp4`，规格为 H.264、yuv420p、576 × 768、16 fps、81 帧、5.0625 秒，SHA-256 为 `173ef1f86bf31909607401b25b2231d12519fa264610a0f66b7ca5e936d0d82b`。原始下载版已归档为 `workflows/validation/orange-longhair-feed-run-v1/cat-feed-orange-longhair-scail2-cn-raw-v1.mp4`，SHA-256 为 `954f191d225c0c652f8dc6d0b3b1e9981a0c0d9555132bf52f60fd89600a818a`。该分支用 `cat-feed-bowl-driver-seedance-v1.mp4` 同时驱动猫、多粒猫粮、猫碗进场、真实入碗进食、抬头复位和猫碗退场，并固定 `replace_mode = true`。

## 真实延迟结论

2026-08-26 在 OneThingAI RTX 4090、¥0.033/分钟的实测：

- 确认开机到 GPU 状态“运行中”：约 22 秒。
- 确认开机到 ComfyUI 真正可访问：约 12 分 54 秒。
- 当前 POC 顺序上传用户图和固定风格图：11.2 秒。
- 队列为空时，Lightning 4 步工作流真实执行：41.1 秒。
- 从确认开机到图片完成：约 14 分 50 秒。

所以“用户点击后再开 OneThingAI”已经被实测否决。若继续使用本地 Qwen，快速预览 worker 必须常驻热机、提前加载模型、固定风格图必须预置，四条视频只能在母版确认后异步排队。即使这样，当前暖机预览仍约 40 多秒，正式上线前必须继续优化或换托管推理，并用 P50/P95 而不是单次最好成绩验收。

当前 SCAIL 单动作实测约 183–226 秒。四个独立暖 GPU worker 真并行时，四动作的当前可兑现等待时间约 3–4 分钟；同一块 GPU 上开四个标签或四个队列仍会串行。母版确认后必须立即提交四条后台任务，同时让用户可跳过地填写宠物名字、生日或年龄、性别和性格等资料；资料填写不得阻塞 GPU。每完成一条视频就即时解锁一个动作，用户离开页面后任务继续，返回时读取持久化状态。界面只显示真实阶段和 `已完成动作数 / 4`，不显示没有依据的百分比。

四卡 CLI 运行器已经实现，使用 `COMFY_GPU_1_URL` 到 `COMFY_GPU_4_URL` 绑定四个不同 ComfyUI endpoint，每卡并发上限为 1，四分支并行提交。它会持久化 prompt ID，丢失 `/prompt` 回包时锁定为未知而不盲目重提，单卡失败时保留其余三条，且对所有 SaveVideo 产物计算真实文件 SHA-256。四卡下载完成后会自动进入同一个中央后处理器，不再把人工调视频当成产品流程。模拟回归已通过；真实 3–4 分钟验收仍需四个同时在线的 4090 endpoint，不会拿单卡模拟冒充实测。运行方法见 `workflows/PARALLEL-4GPU-RUNNER.md`。

网页和四卡 CLI 之间现已加入独立的后台动作调度器。它用磁盘任务记录保存派单状态，同一 `宠物任务号 + 档案号 + 母版 SHA-256` 只能得到同一个动作任务；网页重复 POST、刷新或返回页面不会创建第二批 GPU 任务。调度器重启会读取未完成记录，并让原 CLI 按已保存的 prompt ID 继续。网页只通过服务端密钥访问调度器，视频也由网页接口代理，密钥不会进入浏览器。

默认仍使用已验收的橘猫 POC 缓存，且不启动调度器，因此不会产生额度。以后进行一次明确批准的四卡真实验收时，才在服务端同时设置 `PET_ACTION_USE_KNOWN_CACHE=false`、调度器地址和密钥，并单独启动 `npm run pet:coordinator`。该开关只对哈希完全一致的已编译橘猫合同生效；其他用户母版没有身份档案和编译清单时仍保持阻塞，不能误派到橘猫工作流。

## 视频无缝闭环

用户看到的卡顿有两个不同来源，必须分开处理：原片首尾姿势不一致属于素材问题；浏览器等到 `ended` 才换层、视频尚未完整缓存属于播放问题。只改 CSS、加淡入淡出或手工调某一只猫，均无法形成可复用闭环。

正式流水线固定执行以下合同，任何一关失败都不发布：

1. 四块 GPU 只生成四条原片；运行前先确认本机存在支持 `blend`、`minterpolate`、`ssim` 和 `tpad` 的完整 ffmpeg/ffprobe，缺工具会在花费 GPU 额度之前终止。
2. 对每条原片的第 0 帧和末帧同时做全画面与宠物主体区域 SSIM 检查。全画面必须不低于 `0.90`、主体区域必须不低于 `0.86`。同时分别检查全画面和主体区域的全部 151 组相邻帧，防止中央裁剪漏掉边缘的尾巴、猫碗或背景闪变。这两关都在桥接后处理之前执行，防止把坏原片“抹成合格”。
3. 只有当整批恰好一个分支出现 `SOURCE_SEAM_MISMATCH` 时，才自动换预先保存的第二个确定性 seed，且只重跑这一个分支一次。两个及以上分支同时失败会触发整批保险丝，不再消耗 GPU；进程重启后会从持久化记录恢复这唯一次重试。编码器、网络或工具错误不会触发付费 seed 重试。
4. 合格原片统一编译为 576 × 768、30 fps、152 帧。第 0、1、150、151 帧都是同一张已确认宠物母版；前后各用 10 帧片内桥接，不依赖人工选择 `fade` 或 `mci`。正式编码固定为 H.264 Main Profile、Level 3.1、零 B 帧、最长 30 帧 GOP和 8 Mbps VBV 上限，降低移动设备的实时解码压力。
5. 每条原片下载完成后就进入两路并发的中央收尾器，自动检查编码、Profile、Level、B 帧、关键帧间隔、帧率、帧数、PTS 间隔、解码完整性、四个锚点以及全部 151 组相邻帧。单条全部通过后，以不可变文件和独立分支清单原子发布，页面可以立刻开放；其他三条继续运行。整批结束后再汇总总清单，失败分支没有成片地址，也不会撤掉已经严格通过的兄弟分支。
6. 网页只接受与当前母版 SHA-256、媒体策略和 QA 策略完全一致的已发布分支。每个新 MP4 都使用 `no-store` 完整下载，浏览器重新计算 Blob 的 SHA-256，并验证 MIME、576 × 768、时长和首帧解码；任何一项不符只拒绝该次媒体修订，不把未验收原片交给用户。点击动作时先在 140 ms 内收束到静态母版，再用 `requestVideoFrameCallback` 启动和在第 150 帧交接回待机。

代码入口是 `lib/video/pet-video-finalizer.ts`、`scripts/finalize-pet-video.ts` 和 `scripts/run-pet-action-batch.ts`。生产 worker 必须随镜像打包完整 ffmpeg/ffprobe，或显式设置 `PET_FFMPEG_BIN` 与 `PET_FFPROBE_BIN`；不能依赖开发者电脑上的 TRAE 路径。

## 运行

```bash
npm install
npm run dev
```

打开 <http://localhost:3000/> 。

单条视频可以在不调用 GPU 的情况下复现正式收尾器：

```bash
npm run pet:finalize -- \
  --raw input.mp4 \
  --anchor confirmed-pet-master.png \
  --out output-anchor30.mp4
```

这个命令默认执行严格源片门禁，失败时不会生成可发布文件。`--poc-salvage` 只能略过历史素材的母版首尾身份门禁，仍不能略过原片逐帧跳变、闪屏和冻结检查；四卡自动发布器明确禁止使用该开关。旧的 `smooth:video` 与 `close:seam` 命令仅保留作历史诊断工具，不再是生产发布步骤，也不需要产品运营人员为每只宠物人工判断参数。

当前小灰演示使用 Trework 调用 Seedance 生成的自包含喂食成片 `cat-feed-trework-seedance-poc-v1.mp4`。猫、装有多粒猫粮的食盘、低头进食、抬头复位和食盘退场来自同一条生成视频，不再依赖网页或后期把猫碗贴到无碗动作上。该文件为 H.264、834 × 1112、24 fps、121 帧、约 5.04 秒，SHA-256 为 `34ce02792b6da10a5ab2ca82efaa259e6a6c94ad6de3b994b90f3f5e2c785554`。因成片中的猫只是待机猫的约 84%，页面仅对这个小灰喂食层做 `1.18×` 居中显示校准，不会影响个性化宠物分支。它是当前灰猫 POC 的人工验收版本，不代表任意用户宠物都已拥有可复用喂食分支。

个性化宠物的 SCAIL 喂食成片同样是自包含媒体。当页面播放这种自包含成片时，不得再叠加 DOM 猫碗或猫粮前景，否则会出现双碗和错误遮挡；也不得套用只为小灰示例校准的 `.demoFeedVideo` 缩放与颜色滤镜。个性化分支必须按自身原始尺寸和颜色播放，如果需要新校准，要对该产物单独逐帧验收。

网页舞台现在使用统一纯白底，已去掉舞台边框、圆角、渐变光斑、额外地面阴影和整块 MP4 的 `drop-shadow`。这些效果会将无透明通道的视频画布暴露成一个矩形框，不得在没有重新验收的情况下加回。Trework 喂食成片原始空白区均值约为 248，而待机成片约为 254；只补亮背景后，喂食猫的灰色中间调仍比待机猫深约 6～8 个灰度级。页面最终仅对这个版本的喂食层应用 `contrast(.921) brightness(1.0675)` 两点校准：降低少量对比度抬起猫毛中间调，再恢复白点。更激进的 `contrast(.901) brightness(1.0795)` 会把阴影抬得过浅，已在肉眼对照中否决。当前相邻直立帧取样中，待机与喂食的背景均值分别为 254.410 和 254.406，猫毛主体均值约为 89.44 和 88.32；喂食不再感知为更浅，同时没有回到原始的明显深灰。该参数属于已验收素材的版本参数，不能不经逐帧取样直接套给其他用户宠物。

喂食进出会先等待隐藏视频真正提交一帧，再在同一次绘制中原子切换，不再先露出静止首帧或静止待机帧。已撤销会同时显示两块不透明 MP4 画布的交叉淡入；该做法会暴露白色矩形并造成闪屏，不得再接回。当前仍只是网页 POC 的接缝优化，不等于源视频已精确闭合到待机首帧。上线前还应对该 MP4 做一次不改画面的 faststart 重封装并去掉未使用的 AAC 音轨；若仍能看出纹理跳变，再只处理末尾 0.2–0.3 秒，不需要重新生成整条视频。

首次打开或动作结束后曾出现“白舞台，刷新一次才恢复”。根因有两个：旧实现把等待视频帧超过 80 ms 也误判成“首帧已呈现”，并且待机层使用了通用 `hidden` 类，被 Tailwind 变成 `display:none`，导致隐藏期间无法向合成器提交新帧。现在超时提高到 1200 ms 且返回失败，只有真实 `requestVideoFrameCallback` 才算成功；待机层改用只调整透明度的 `mediaHidden`，仍保留在绘制树里。页面另有一个高优先级静态母版层，只有视频帧真实呈现后才隐藏；首次进入、页面恢复以及个性化宠物待机都不再依赖刷新。

`cat-feed-bowl-transition-local-v5.mp4` 是已否决的本地叠碗实验，不得再接入演示或产品路径。失败原因不是简单坐标误差，而是原始头部动作没有围绕猫碗生成；后贴碗无法建立可信的嘴、舌头、粮面和碗沿遮挡关系。正式版必须从首帧或首尾帧阶段就把装有多粒猫粮的猫碗作为动作条件生成，不能继续在无碗动作上补贴素材。

```bash
npm run preview:feed -- \
  public/assets/generated/cat-idle-scail2-poc-smooth30-v1.mp4 \
```

该脚本只用本机 ffmpeg，并保留作为失败样本的复现工具。它不能解决原始动作与猫碗几何不一致的问题，不得再用于页面主媒体或产品生成。猫碗素材的生成提示词和抠图约束保存在 `workflows/prompts/cat-food-bowl-asset-v2.md`。

对于新的、从未生成过的照片，服务端需要一个受保护的 ComfyUI HTTPS 入口。复制 `.env.example` 到本地环境文件，只在服务端填写：

```text
COMFY_BASE_URL=https://...
COMFY_AUTH_COOKIE=...
```

不要使用 `NEXT_PUBLIC_` 变量，不要把 OneThingAI 临时反代地址、Cookie 或其他授权信息提交进仓库。

## 尚未完成的产品化工作

- OneThingAI 当前是临时浏览器会话，不是可供公开用户长期调用的稳定生成后端。要真正上线，必须改成稳定、受保护的 HTTPS 入口。
- 当前还没有独立的宠物特征识别服务。工作流会要求 Qwen 先检查毛长、毛量、脸型、眼色、耳饰毛和尾巴，但产品化仍应先输出结构化“宠物身份合同”，让用户确认高影响特征，再动态拼提示词并做生成后复检。
- 当前任务状态只在本地内存保存一小时。生产环境需要 R2 存图、D1 或等价数据库存任务和审核状态。
- 当前恢复键和任务接口是单机单用户 POC，没有登录用户归属校验。同一浏览器切换账号会有串宠风险；正式发布前必须把 `petId/jobId` 绑定 `userId`，并对任务读取、图片读取和确认接口逐个做服务端授权，不能只靠 localStorage。
- 公开生成按钮前必须加登录、限频和每用户额度，否则任何人都可以脚本化烧 GPU 费用。因此当前代码只允许 `localhost` 提交新的 GPU 任务，非本地环境默认拒绝。
- 同一次上传会携带幂等键；网络重试只会找回原任务。进度查询失败时也不会把“继续查询”变成新一次付费生成。
- 狗狗固定风格母版还没有验收，页面已明确禁用狗狗选项，不会把狗套进猫模板。
- 四卡 CLI 已接入独立的持久化后台调度器；默认无调度配置时接口仍安全停在 `plan_only`。正式上线还需要把当前单机磁盘任务记录迁移到平台数据库、把成片迁移到对象存储，并绑定真实用户权限。
- 真实四卡并行还未在四个同时在线的 4090 endpoint 上完成计时验收；当前通过的是四 worker 模拟集群与安全性回归。

工作流、节点绑定和恢复步骤见 [`workflows/README.md`](workflows/README.md)。
